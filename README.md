# TicketPoint

Управляйте билетными бронированиями, клиентами и мероприятиями в одном рабочем пространстве. TicketPoint объединяет настольное приложение и веб-интерфейс с общей PostgreSQL: изменения доступны обоим клиентам после обновления.

## КР №3: backend

Реализованы Spring Data JPA, Flyway, JWT/refresh-сессии, BCrypt, UUID, архив, теги, заметки, безопасные фильтры, серверные страницы, CSV preview/apply, аналитика и аудит. Веб-клиент использует REST API, подготовленный для Android.

- Проверка на временной PostgreSQL: `./backend/verify-kr3.sh`.

Добавьте в `.env` ключ `JWT_SECRET_BASE64` (32 случайных байта в Base64). В текущем локальном `.env` ключ уже добавлен; пример настроек не содержит секретов.

В веб-интерфейсе КР №3 USER просматривает свои данные, MANAGER редактирует бронирования, ADMIN управляет справочниками и пользователями. Дополнительные возможности настольного JDBC-клиента КР №2 описаны ниже.

## Возможности настольного клиента КР №2

- **Бронирования.** Создание билета, карточка со связанными данными, редактирование клиента и мероприятия до оплаты, смена статуса и удаление с подтверждением.
- **Справочники.** Администратор создаёт, исправляет и удаляет клиентов и мероприятия. Связанные записи выбираются из списка.
- **Поиск.** Номер билета, имя и код клиента, название и место мероприятия.
- **Фильтры.** Статус, клиент, мероприятие и период дат; фильтры работают совместно.
- **Сортировка.** По столбцам таблицы, включая дату, цену и статус; Shift позволяет сортировать по нескольким столбцам.
- **Аналитика.** Всего бронирований, новые, подтверждённые, оплаченные, отменённые, билеты от 5 000 ₽ и доля оплаченных.
- **Экспорт.** Текущий список из настольного приложения в Excel с сохранением фильтров и порядка строк. Место сохранения выбираете вы.
- **Доступ.** Самостоятельная регистрация покупателей, вход по логину и паролю, смена пароля, роли и управление учётными записями. Почта не требуется.

Номер билета и код клиента создаются автоматически. Цена фиксируется при бронировании. Билеты можно выпускать только на будущие мероприятия. Пользователь отправляет новую заявку. Менеджер подтверждает её, затем отмечает полученную оплату: «Новое → Подтверждено → Оплачено». Неоплаченную заявку можно отменить; оплаченный билет отменяет сотрудник. Отменённый билет остаётся доступным для просмотра.

## Быстрый старт

Нужны **Java 21+**, **Docker с Compose** и графическое окружение для настольного приложения. Maven загружается через Wrapper. Первый запуск требует доступа к интернету.

1. Создайте файл настроек из `.env.example`:

   ```bash
   cp .env.example .env
   ```

   В Windows: `Copy-Item .env.example .env`. Существующий `.env` сохраняйте.

2. Заполните `POSTGRES_PASSWORD`, `BOOTSTRAP_ADMIN_PASSWORD` и `JWT_SECRET_BASE64` в `.env`. Пароль администратора должен содержать 8–128 символов. Логин по умолчанию — `admin`; его можно изменить через `BOOTSTRAP_ADMIN_LOGIN`.

3. Запустите Docker, затем сервер и базу:

   ```bash
   docker compose up -d --build --wait
   ```

4. Откройте [веб-приложение](http://localhost:8080/) и проверьте [состояние сервера](http://localhost:8080/actuator/health): ответ должен содержать `UP`. Войдите и замените временный пароль.

5. Запустите настольное приложение из корня проекта:

   ```bash
   ./run.sh
   ```

   В Windows:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\run.ps1
   ```

Оба клиента используют одну учётную запись. В JavaFX войдите с уже изменённым паролем. Настольное приложение подключается к PostgreSQL непосредственно через JDBC и работает независимо от доступности веб-сервера.

На пустой базе создаются таблицы и примеры: 5 клиентов, 3 мероприятия и 10 бронирований. Данные хранятся в Docker volume и сохраняются после остановки. Для альтернативного расположения Compose используйте `docker compose --env-file .env -f backend/docker-compose.yml up -d --build --wait`.

## Пользователи и роли

| Роль          | Возможности                                                                                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Покупатель    | Афиша, создание заявки только на себя, свои билеты и статистика, исправление новой заявки, отмена неоплаченной заявки до начала события, удаление своей новой заявки, экспорт своих данных |
| Наблюдатель   | Просмотр билетов, справочников, заметок и статистики, поиск и экспорт; изменение данных запрещено                                                                                          |
| Менеджер      | Все заявки, создание за клиента, исправление новых заявок, подтверждение, возврат на исправление, отметка полученной оплаты, отмена; удаление новых и отменённых записей                   |
| Администратор | Операции менеджера, общая статистика, CRUD справочников, создание учётных записей, изменение имён и ролей, управление доступом                                                             |

Покупатель регистрируется самостоятельно на экране входа: имя, логин, пароль и его подтверждение. После регистрации сразу открывается личный кабинет. Роль всегда «Покупатель», профиль клиента создаётся автоматически; выбирать чужое имя при бронировании нельзя. Выбранный самостоятельно пароль постоянный, менять его повторно при первом входе не нужно. Логин уникален без учёта регистра. Учётная запись и профиль создаются одной транзакцией.

Администратор создаёт менеджеров и дополнительные учётные записи через вкладку «Пользователи» или веб-интерфейс. Для выданных администратором учётных записей сохраняется обязательная смена временного пароля. Самостоятельно получить роль менеджера или администратора нельзя.

Веб-интерфейс и JavaFX поддерживают регистрацию покупателя. Доступные мероприятия находятся во вкладке «Мероприятия» в браузере и «Афиша» в JavaFX. Кнопка «Забронировать» открывает форму с выбранным мероприятием; профиль покупателя подставляется автоматически. Статусы и действия сотрудника недоступны покупателю и проверяются на сервере. В веб-интерфейсе есть фильтр архивных билетов; восстановление выполняет сотрудник. JavaFX показывает только текущие записи. Самостоятельная регистрация создаёт роль USER, даже если в запрос добавлены другие роли.

Роль VIEWER предназначена для наблюдателей: чтение разрешено, изменение данных запрещено. Учётную запись наблюдателя создаёт администратор. При запуске JavaFX эта роль сохраняется. Уже переведённые прежними версиями в USER аккаунты не меняются автоматически; администратор может назначить им роль VIEWER. Существующие билеты не назначаются человеку по совпадению имени. При изменении роли личный профиль сохраняется. Изменение имени или роли и отключение доступа отзывают старые сеансы. JavaFX не позволяет отключать или понижать администраторов; REST API защищает текущего и последнего активного администратора.


Логин содержит 3–40 символов: латинские буквы, цифры, точку, дефис или подчёркивание. Регистр не учитывается. Новые пароли содержат 8–128 символов, не более 72 байт UTF-8 и сохраняются BCrypt с индивидуальной солью (cost 12). Старые PBKDF2-хеши поддерживаются и обновляются при успешном входе в backend. После пяти неверных попыток вход блокируется на пять минут. Веб-клиент использует access JWT на 15 минут и refresh-сессию на 14 дней; настольный сеанс действует 30 минут после входа. Смена пароля делает прежние сеансы недействительными.

Начальный администратор создаётся только при отсутствии учётных записей. Изменение `BOOTSTRAP_ADMIN_PASSWORD` в `.env` не заменяет пароль существующей записи.

## Подключение и настройки

Параметры хранятся в `.env`, исключённом из Git. Переменные окружения имеют приоритет.

| Переменная                     | Значение по умолчанию                          | Назначение                         |
| ------------------------------ | ---------------------------------------------- | ---------------------------------- |
| `POSTGRES_DB`                  | `ticketpoint`                                  | Имя базы Docker                    |
| `POSTGRES_USER`                | `ticketpoint`                                  | Пользователь PostgreSQL            |
| `POSTGRES_PASSWORD`            | Задайте своё                                   | Пароль PostgreSQL                  |
| `POSTGRES_PORT`                | `5433`                                         | Порт базы на компьютере            |
| `BACKEND_PORT`                 | `8080`                                         | Порт веб-приложения                |
| `DB_URL`                       | `jdbc:postgresql://localhost:5433/ticketpoint` | JDBC-подключение                   |
| `DB_USER`                      | `${POSTGRES_USER}`                             | Пользователь подключения           |
| `DB_PASSWORD`                  | `${POSTGRES_PASSWORD}`                         | Пароль подключения                 |
| `APP_ZONE`                     | `Europe/Moscow`                                | Часовой пояс мероприятий           |
| `BOOTSTRAP_ADMIN_LOGIN`        | `admin`                                        | Первый администратор               |
| `BOOTSTRAP_ADMIN_NAME`         | `Administrator`                                | Имя первого администратора         |
| `BOOTSTRAP_ADMIN_PASSWORD`     | Задайте своё                                   | Временный пароль администратора    |
| `COOKIE_SECURE`                | `false`                                        | `true` при веб-доступе через HTTPS |
| `DB_CONNECT_TIMEOUT_SECONDS`   | `5`                                            | Ожидание подключения               |
| `DB_STATEMENT_TIMEOUT_SECONDS` | `15`                                           | Ограничение выполнения SQL         |
| `DB_SOCKET_TIMEOUT_SECONDS`    | `30`                                           | Ожидание ответа PostgreSQL         |

Если порт базы занят, измените одновременно `POSTGRES_PORT` и порт в `DB_URL`. При изменении имени базы обновите `POSTGRES_DB` и `DB_URL`.

Для существующей PostgreSQL задайте `DB_URL`, `DB_USER` и `DB_PASSWORD`. APP_ZONE применяется и к бизнес-проверкам REST backend, и к JDBC, и к локальным датам создания/изменения.

Схема предметной области описана в [db/schema.sql](db/schema.sql). Flyway-миграции V1–V4 применяются автоматически при запуске backend; миграции учётных записей и личных профилей также поддерживаются при первом входе из JavaFX; существующие клиенты, мероприятия и бронирования сохраняются. Пользователю БД нужны права на создание таблицы `app_users`; при отдельном развёртывании её может заранее создать администратор по [002-auth.sql](db/migrations/002-auth.sql).

Порты Docker опубликованы только на `127.0.0.1`. Для сетевого веб-доступа настройте HTTPS на обратном прокси и `COOKIE_SECURE=true`. REST API использует Bearer JWT и проверяет права независимо от интерфейса. Токены веб-клиента хранятся в памяти вкладки. Отдельная HttpOnly/SameSite cookie используется только для чтения Swagger; для операций API эта cookie не принимается.

## Работа с приложением

Администратор создаёт мероприятия и учётные записи сотрудников. Покупатель нажимает «Нет аккаунта? Зарегистрироваться», указывает имя, логин и пароль с подтверждением. После регистрации пользователь открывает «Мои билеты», нажимает «Забронировать билет» и выбирает будущее мероприятие. Его профиль подставляется автоматически. Менеджер открывает заявку, выбирает «Подтверждено», затем после получения оплаты — «Оплачено». Приложение учитывает факт оплаты; банковские платежи и возвраты выполняются вне приложения.

У новой заявки до начала мероприятия можно изменить мероприятие, сохранив статус «Новое»; сотрудник также может исправить клиента. При смене мероприятия применяется его текущий тариф, для прежнего мероприятия цена сохраняется. Номер билета и дата создания не меняются. Подтверждённую заявку менеджер может вернуть в «Новое» для исправления. Оплаченный билет можно отменить, но нельзя менять его реквизиты или удалять напрямую. Отменённую запись нельзя возобновить: создайте новую заявку. В текущей общей базе удаление из JavaFX перемещает запись в архив. Покупатель может убрать свою новую заявку; менеджер — новую или отменённую. В REST API сотрудники могут архивировать записи независимо от статуса. Окончательное удаление выполняет только администратор через REST API или веб-интерфейс, после архивирования и подтверждения.

Справочники изменяет только администратор. В текущей общей базе действие удаления мероприятия в JavaFX отключает его для новых бронирований; включить его снова можно в веб-интерфейсе. Ссылки и история сохраняются. Клиенты, связанные с билетами или учётными записями, защищены внешними ключами от удаления. Изменение тарифа мероприятия не меняет цену уже созданного бронирования. Устаревшая форма не перезаписывает изменения другого сотрудника.

Поиск и фильтры можно комбинировать. Если запись исчезла после обновления, проверьте выбранные фильтры. Нажмите «Обновить», чтобы получить изменения других пользователей. Статистика сотрудника рассчитывается по всей базе, пользователя — только по его билетам. «Экспорт Excel» сохраняет видимый список с текущей сортировкой.

Ошибки ввода отображаются рядом с формой. Ошибки соединения, прав и файлов показываются понятными сообщениями; технические подробности настольного приложения записываются в `logs/ticketpoint-*.log`.

## Консольная версия КР №1

Консольное приложение находится в модуле `core`, главный класс — `ru.ticketpoint.ConsoleApplication`. Оно подключается к PostgreSQL напрямую через JDBC. Настройки `DB_URL`, `DB_USER`, `DB_PASSWORD` и `APP_ZONE` читает из `.env` в рабочем каталоге; используйте корень проекта как Working directory.

Сначала подготовьте `.env` и запустите базу и backend по инструкции «Быстрый старт» выше. Backend применит миграции Flyway и добавит начальные данные. После подготовки схемы консольному приложению достаточно доступной PostgreSQL.

Запуск из корня проекта на macOS/Linux (без запуска тестов):

```bash
./mvnw -pl core -Dmaven.test.skip=true compile org.codehaus.mojo:exec-maven-plugin:3.5.1:java -Dexec.mainClass=ru.ticketpoint.ConsoleApplication
```

В Windows PowerShell:

```powershell
.\mvnw.cmd -pl core "-Dmaven.test.skip=true" compile org.codehaus.mojo:exec-maven-plugin:3.5.1:java "-Dexec.mainClass=ru.ticketpoint.ConsoleApplication"
```

В IntelliJ IDEA откройте корневой `pom.xml`, выберите JDK 21+, создайте конфигурацию Application с главным классом `ru.ticketpoint.ConsoleApplication`, classpath модуля `core` и рабочим каталогом в корне проекта.

После запуска откроется интерактивное меню: клиенты, мероприятия, бронирования, поиск, фильтрация, сортировка, статистика, экспорт Excel и список таблиц БД. Пункт `0` возвращает назад или завершает приложение из главного меню. Пункт `8` сохраняет `.xlsx` в каталог `exports` относительно корня проекта.

## Сборка

```bash
./mvnw clean package
```

В Windows используйте `.\mvnw.cmd`. Для запуска из IntelliJ IDEA откройте корневой `pom.xml`, выберите JDK 21+ и укажите корень проекта как Working directory. Главный класс — `ru.ticketpoint.fx.FxLauncher` в модуле `javafx-client`.

Готовое настольное приложение:

```bash
java -jar javafx-client/target/javafx-client-1.0.0.jar
```

JAR включает JavaFX для платформы сборки; для другой ОС выполните сборку на ней. Серверный JAR — `backend/target/backend-1.0.0.jar`; при запуске вне Docker сервер по умолчанию слушает `127.0.0.1:8080`. `SERVER_ADDRESS` и `SERVER_PORT` меняют эти настройки.

## Проверка

```bash
./mvnw test
```

Для полной проверки на отдельной временной PostgreSQL:

```bash
RUN_FX_TESTS=true bash backend/verify-kr3.sh
```

Скрипт запускает отдельный контейнер, выполняет все модули `clean verify` и удаляет только свой контейнер. Оконные тесты требуют графического окружения. Без `RUN_FX_TESTS=true` они пропускаются.

При ручном запуске тестов используйте исключительно отдельную тестовую БД. JDBC/JavaFX используют `TEST_DB_URL`, `TEST_DB_USER`, `TEST_DB_PASSWORD`. Backend использует `KR3_TEST_DB_URL`, `KR3_TEST_DB_USER`, `KR3_TEST_DB_PASSWORD` и применяет Flyway в предоставленной базе; его сценарии записывают тестовые данные. Не указывайте рабочую БД. Одного `./mvnw test` без этих параметров недостаточно для запуска интеграционных сценариев.

## Архитектура

```text
core/             Модели, сервисы, JDBC-репозитории, авторизация и экспорт
javafx-client/    Настольный интерфейс: FXML, контроллеры и CSS
backend/          Spring Boot, REST API и веб-интерфейс
db/               Схема, примеры данных и миграции
```

JavaFX → Service → Repository → PostgreSQL. Веб-интерфейс → REST API → backend service → Spring Data JPA → PostgreSQL. SQL находится в репозиториях, бизнес-ограничения — в сервисах и моделях; операции ввода-вывода JavaFX выполняются в фоновом потоке.

## Обслуживание

- **Нет соединения с базой:** проверьте `docker compose ps`, адрес и порт JDBC. PostgreSQL должен быть доступен и иметь статус `healthy`.
- **Пароль базы не принят:** сверьте настройки подключения. Изменение `.env` не меняет пароль пользователя в существующем хранилище PostgreSQL.
- **Несовместимая структура базы:** проверьте выбранную базу и применённые миграции. Схему backend создаёт и обновляет Flyway; проверьте историю `flyway_schema_history`.
- **Вход временно недоступен:** после пяти ошибок подождите пять минут; администратор может проверить состояние доступа.
- **Сеанс завершён:** войдите заново. Это также происходит после смены пароля или отключения учётной записи.

Остановка с сохранением данных:

```bash
docker compose stop
```

Перед обслуживанием базы сохраняйте резервную копию. Не удаляйте Docker volume, если данные должны сохраниться.

## Начальное наполнение

После запуска backend (Flyway V1–V4) загрузите данные явно:

```bash
psql "$DB_URL_PSQL" -v ON_ERROR_STOP=1 -f db/initial-data.sql
```

`DB_URL_PSQL` — строка подключения PostgreSQL вида `postgresql://localhost:5433/ticketpoint`; имя и пароль можно передать через `PGUSER` и `PGPASSWORD`. Для Compose: `docker compose exec -T postgres psql -U ticketpoint -d ticketpoint < db/seed.sql`, затем выполните `initial-data.sql` через локальный psql, чтобы работал относительный `\ir`.

Для чистой установки можно сразу задать `BOOTSTRAP_ADMIN_PASSWORD=admin12345`. Эти известные пароли предназначены для проверки функционала; перед публичным развёртыванием смените их.

Для регистронезависимого поиска на русском языке PostgreSQL должна использовать Unicode-совместимую локаль (например `en_US.utf8` или ICU `ru-RU`). База с `LC_CTYPE=C` некорректно приводит кириллицу к нижнему регистру. Проверка: `SELECT lower('ДЖАЗОВЫЙ');` должна вернуть `джазовый`.
